1. **Node.js 22.18 or newer** (nodejs.org, the LTS installer). Check: `node -v` shows `v22.18` or higher.
2. **Git** (git-scm.com). Check: `git --version`.
3. **Tailscale**, signed in to the same tailnet as the VPS. Needed to read the shared surface and for any

4. (For StarNet) nothing extra: `npm install` inside StarNet brings what it needs.

Each `profile add` prints the bot's token **once**. Store it in that bot's secrets on the VPS. Tokens are kept

```bash

npm run profile -- add --id dm --role dm
```


## 5. How the system works

### 5.1 The event ledger: the single source of truth
- **Append-only, in SQLite.**
  - The database itself refuses UPDATE and DELETE (triggers).
  - Every event is **SHA-256 hash-chained** to the one before it.
  - The server verifies the whole chain at start and refuses to run if it's broken.
- **Event fields:** `seq`, `ts`, `type`, `kind` (intent/fact), `city` tag, `subject`, `payload`, `actor`,
  `authorizedBy`, `hash`.
- **IDs are global, monotonic and never reissued:**
  - cities: slug of the name
  - districts `DST-000001`, departments `DPT-000001`, agents `AGT-000001`
  - social channels `CHN-…`, posts `PST-…`, inbox messages `MSG-…`

  Deleted agents' **IDs and names are retired forever**.
- **The projection** (`state.ts`) rebuilds the world from the ledger on start and applies each new event
  live.

### 5.2 How writes flow
1. Marc does something in the dashboard, which writes an **intent** (`intent.*`). An intent changes nothing
   by itself.
2. The DM **routes** it (`dm.routed`).
3. The Mayor (or the DM, for world events) writes the **fact**, citing the intent (`authorizedBy`).
   - The guard checks the fact matches the intent exactly, for the same city, and that the intent wasn't
     already used.

Placing, promoting, moving and deleting agents, and creating structure, all need this chain. **No agent
executes its own exit, move or promotion.**

### 5.3 A19: Marc never waits
- When Marc submits, the server immediately routes and carries out his request, acting as **`marc-as-dm`** and
  **`marc-as-mayor`**, through the same guard.
- If the rules refuse, the form says why, and the request stays under **Activity → Unfinished requests**,
  with **Apply**.
- The bots still do the city's own work and can carry out anything left waiting.

### 5.4 The write-guard (`guard.ts`)
Every write passes:
1. **Role check:** who may write this type.
2. **Scope check:** a Mayor writes only its own city's tag; cross-city writes are rejected.
3. **Schema check:** strict; unknown fields are rejected. Bot tokens can never enter the ledger, only a
   `botTokenRef`.
4. **Authorization match**, where required.
5. **The world's rules** (section 6).

### 5.5 Reading
- **Who sees what:** Marc, the DM, Bob and the Essentials Mayors see every city; other Mayors only their own.
- `/api/state` returns the filtered world.
- `/api/stream` pushes each new event live (Server-Sent Events, with resume).
- The dashboard redraws on every change, keeping open panels and focus. 3D pages redraw only when the ledger
  actually changed.

### 5.6 Around the ledger
- **DM webhook:** a signed ping on each intent. The ledger is still the DM's queue, so a missed ping loses
  nothing.
- **Demo autopilot:** `demo.db` only. It plays the DM and the Mayors, answers chats, and reworks rejected
  posts. It refuses to attach to any other file.
- **Social publisher:** every 30 s it posts approved, due posts through platform connectors. None are
  connected yet, so due posts wait for "Mark as posted".
- **StarNet stations:** one per city, supervised. See section 10.
- **Surface feed:** reads the VPS reader every 15 s. See section 11.

## 6. The world's rules

The full wording is in `docs/source/WORLD-BUILD-BRIEF.md` (authoritative), `docs/BRIEF-AMENDMENTS.md` and
`docs/constitution/WORLD-CONSTITUTION.md`. Everything below is enforced by the ledger unless marked
"Hermes-side".

### 6.1 World model
```
WORLD (Marc) — only the DM and Bob cross between cities, read-only (plus Essentials read-only, A2)
 └ CITY — Mayor + bot; FAMILY = revenue | claude | gemini | essentials
    ├ COLLEGE — dean + professors; where agents and professors are created (A11–A14)
    └ DISTRICT — supervisor
       └ DEPARTMENT — the agents who specialise in it (no slots, A8); optional caps (A9)
          └ AGENT — unique never-reused ID
```
- **DM routes / Mayor runs / Bob designs / Innovations vets + Security monitors.** Mayors don't route to each
  other.
- **Family limits:** Claude and Gemini hold **one city each** (a second is rejected); Revenue gets the most
  map room (A17).

### 6.2 Identity
- A unique, never-reused ID is the identity; the name is a label.
  - Deleted IDs and names are retired forever (strict reading; open question #1 in OPEN-QUESTIONS).
- **Canonical identity record:** ID, name, placement card, tier, graduation state, ledger pointer, own memory
  scope.
- **Name generator (A5):** a blank name gets one generated. It never repeats a retired name, a living
  agent's, a Mayor's, Marc's or Bob's.

### 6.3 Lifecycle
- **States:** `enrolled` (created at the college, not placed) → `student` (placed) → `probationer`
  (graduated) → `active` → `senior`. **Dept-lead** is a badge on a senior, only with 3+ graduated agents in
  the department.
- **Lifecycle strip:** enrollment → school → graduation → active → promotion → school-return → 3rd-strike →
  deletion.
- **KPI misses:** miss #1 and #2 send the agent back to school; miss #3 is the 3rd strike, and deletion
  follows. Only probationer, active or senior agents can take KPI strikes.
  - On deletion the full ledger is frozen and archived, and a sanitized **lesson record** is the
    replacement's first curriculum.
  - "Lessons persist, the individual doesn't."
- **Promotions** above graduation, placement, moves and deletion need Marc's request (carried out by the
  Mayor).
- **Shadows = interns (A7, A8):**
  - A student in the last phase before graduation, attached to its department (not to one agent).
  - **The Mayor appoints** student → intern → graduated on its own.
  - Graduation needs a **passed exam from a professor of that department** (A10).
  - Going back to school means doing the internship and exam again.
- **Caps (A9):** optional limits on graduated agents and on shadows per department.
- **Delegation (A9, option B):**
  - A graduated agent may hand a task from the department's approved **basic tasks** list to a shadow in its
    own department.
  - Every hand-off is logged (`task.delegated` / `task.returned`), and the result comes back as data.
  - **No other agent-to-agent instruction is allowed.**

### 6.4 College, professors, dean (A10–A16)
- **Where agents come from:**
  - Agents and professors are created **only at the college**.
  - **Adding an agent to a department assigns an existing agent of that city; it never creates one.**
- **Professors:**
  - They teach, examine and judge graduation.
  - They specialise in a department (set at creation or later, within the city).
  - They stay at the college and **step in** only when their department reports an unfilled role, for a set
    time (up to 30 days), then return.
  - A **senior** can retire into a professor, keeping its ID and name.
- **Professors' strikes:**
  - No KPI or task strikes; only **teaching strikes** (from Security, observed by a deployed agent).
  - 3 = held awaiting deletion.
  - Each keeps a **teaching record**: exams given, exams passed, graduates.
- **The dean:**
  - One per college; Marc creates the first.
  - Scored on **how its graduates perform**: graduates, still working, promoted past probation, KPI strikes,
    jail terms, deleted.
  - **The Mayor reviews the dean** (exceeds / meets / below); consequences are to be decided after testing.
  - Deans **report** agents not doing their work to Security, which **escalates to Marc** (the Inbox).
  - **Replacing a dean:** an outstanding professor becomes dean; the old dean goes back to teaching.

### 6.5 Security and the jail (A3, A6, A15)
- **Deployment and strikes:**
  - Marc deploys a graduated Security agent to a city.
  - When it catches an agent not doing a task, Security's Mayor records a **task strike**. This is a
    separate counter from KPI strikes.
- **Jail:**
  - Every 3rd task strike = jail: 6 h, then 24 h, then 3 days. Terms end on their own; task strikes reset
    after each term; the level never resets.
  - The 4th jailing, or a 3rd KPI strike, means **held awaiting deletion**.
  - Deletion happens only from there, and only on Marc's request.
  - While jailed, an agent can't graduate, be promoted, move, or take strikes.

### 6.6 Economy (A18, phase 6)
- **Currency:** dollars, kept in cents.
- **Earning:** only from **real-revenue deliverables** of **active or senior** agents, vetted by Marc + Mayor.
  - More than **one QC rework in a week** (weeks start Monday) loses that week's credit.
  - Amounts are set per grant.
- **Spending:** only on rewards R1–R5:
  - **R1** role-scope / cloud-lane upgrades
  - **R2** city access (never cross-city)
  - **R3** dept-lead / mentorship (3+ agents)
  - **R4** tenure / first-retry grace (never deletion-immunity)
  - **R5** Hall of Agents
- **Express non-rewards are rejected:** authority, cross-city reach, auto-publish, skipping school,
  memory/knowledge, ledger exemptions, deletion-immunity, essentials.
- **Graduation vetting gate:** Innovations' vetting record.
- **No agent holds or spends its own money.**

### 6.7 The inviolable floor (brief)
1. The ledger is inviolable; daily recording is a duty, never economy-gated.
2. Memory and knowledge are never scarce or for sale.
3. Essential operations are never economy-gated.
4. No auto-publish (Social enforces it).
5. No cross-city write or execution.

### 6.8 World Constitution (phase 7)
- **Articles I–XII** in `docs/constitution/WORLD-CONSTITUTION.md`.
- **In force only if the file matches the fingerprint ratified in the ledger.** 1.0.0 is ratified by
  `npm run seed`.
- SOULs **reference it by one pointer line** and never copy or soften it. `npm run constitution -- check`
  verifies this.

## 10. StarNet (A20)

- **What it is:** an open-source local agent harness with a pixel-art station UI. Rooms are capability
  scopes, placed objects are tool grants, conveyor belts are real work routing.
- **How we run it:**

  - Health is checked every 10 s; a station is restarted with backoff if it stops. New cities get a station
    at once.
  - Only station errors print in the terminal (`STARNET_VERBOSE=1` for everything).

  - Runs are autonomous: StarNet refuses anything not granted.
- **Tested here:** 7 real stations up; the station embedded; a chat answered through StarNet (with a stand-in
  model provider).
- **Limits:**
  - Your agents don't appear as crew on the station floor yet (StarNet's roster is owned by its page).
  - Stations only open on the PC itself.
  - Each station needs a model provider.
- **Size note:** StarNet's full repo is 3.3 GB (website, docs, art sources). Our planned copy ("inside this
  project", A21) will keep only our changes plus a pinned StarNet version fetched by one setup command.

## 11. Hermes, Mnemosyne and the shared memory surface (A21)

### 11.1 Marc's decisions
- **No copies.** A world agent *is* one of Marc's Hermes agents (a profile) with its own Mnemosyne memory.
  StarNet's own "import a Hermes agent" makes a one-time copy, which won't work.
- **Our copy of StarNet** will live inside this project and "create agents from my setup".
- **Hermes runs on the VPS; the world on the PC.**
- **Agents are made only by Marc (dashboard), or by the DM, a Mayor or the Architect when Marc tells them.
  Never automatically.**

### 11.2 The shared-memory spec (Innovations, `docs/SPEC-2026-09-26-SHARED-MEMORY-FOUR-TIER.md`)
- **One shared surface** (one SQLite file, one writer), not one per city:
  `/home/hermeswebui/.hermes/mnemosyne_shared/surface.db`.
  - Reached by the config key `memory.mnemosyne.shared_surface_path` through the `mnemosyne_shared_*` tools.
- **Every note has four tags:**
  - `city`: a city, or `WORLD` for the world layer (the "zero-th city")
  - `dept`: a department, `governance` for city level, or `world`
  - `agent`: an agent, or `—`
  - `kind`: one of **roster, kpi, status, dispatch, lesson, policy, note, lifecycle**
- **Three layers:**
  - **WORLD:** constitution, manifests, DM routing, Bob's blueprints. DM, Marc and Bob read and write it.
  - **CITY:** `dept=governance`. The Mayor writes; the Mayor and the city's agents read.
  - **DEPARTMENT/AGENT:** dispatch, lifecycle, lessons, status. The supervisor owns it; the agent writes only
    its own notes.
- **Read/write matrix, enforced physically:**
  - DM, Bob and Marc read everything.
  - A Mayor reads its own city plus WORLD, and writes its own city's governance notes.
  - A supervisor reads its own city and department plus WORLD.
  - An agent reads its own department/agent notes, its city's governance, and WORLD; it writes only its own
    note/status/lesson.
  - No cross-city writes, ever.
- **Private banks:** each agent's identity, full memory and **daily ledger (always recorded, inviolable)**.
  The surface carries only coordination.
- **The dashboard reads the surface read-only, never as a second writer** (SQLite WAL: one writer, many
  readers).

### 11.3 What's built
- **The reader, `vps/surface_reader.py`** (Python standard library):
  - Opens `surface.db` with SQLite **read-only mode + `query_only`**. Any write request answers 405.
  - Serves `/health` and `/notes?after=&limit=` over Tailscale, with a bearer token.
  - Reads Mnemosyne's `working_memory` and `episodic_memory` tables.
  - Takes the four tags from note **metadata** (`city`, `dept`, `agent`, `kind`, or nested under `world`),
    or from a first line `city=… dept=… agent=… kind=…`. Flags missing tags.
  - **Tested against a database written by the real Mnemosyne code:** it read all tags, flagged an untagged
    note, picked up live writes, and left the file byte-identical.
- **The world's feed** polls the reader every 15 s, maps surface city names to world cities
  (`config/surface-cities.json`), and applies the matrix per viewer.
- **The Memory tab:**
  - Live status per agent, KPI pulses, and every note with its tags.
  - Filters: city (including WORLD), department, kind, text.
  - Warnings for unmapped cities and untagged notes.

### 11.4 Important finding for the Messenger
- Mnemosyne's stock `mnemosyne_shared_remember` accepts only kinds **meta / preference / correction /
  identity** and has **no city/dept/agent fields**.
- So the spec's four tags must ride in the note's **metadata** (recommended: `{"city","dept","agent","kind"}`,
  `kind` being one of the eight) or a first content line.
- **Please decide before agents write**, and extend the physical-scoping guard to check the tags.

### 11.5 Still to build (waits on open questions #1–#3)
1. **The Hermes link.** Our StarNet copy hands each agent's turn to its Hermes profile over Hermes's API
   server, so it answers with its own persona, tools and Mnemosyne memory. Nothing is copied.
2. **Creating agents.** When Marc creates an agent (dashboard or instruction), the DM builds its Hermes
   profile and private bank as part of carrying out that request, and reports it back.

## 12. What the bots connect to: the API

|---|---|---|---|

| GET | `/api/me` | any login | the caller's profile |

| GET | `/api/events?after=&limit=` | any login | raw events, filtered; page with `next` |
| GET | `/api/stream?after=` | any login | live events (SSE: `ledger`; `surface` = refresh hint) |

| POST | `/api/intents/<seq>/create-now` | owner | apply an unfinished request now |
| GET | `/api/names?count=5` | owner | suggested agent names |
| POST | `/api/secrets` | owner | store a bot token as a server secret (the ledger keeps only its name) |

## 14. Security measures

- **Ledger:** append-only (database triggers), hash-chained, verified at start; strict payloads; secrets can
  never enter it.
- **Write-guard:** roles, city scopes, exact intent matching, single use, and all the world's rules.
- **Reading:** each viewer sees only their scope (Mayors their own city).
- **Web:**
  - A strict Content-Security-Policy (no inline code; frames only from `127.0.0.1`/`localhost` for
    stations).
  - HttpOnly, SameSite=Strict, Secure cookies.
  - A required header on browser writes (CSRF).
  - Sign-in throttling.
  - Ledger text is always shown as text, never HTML.
  - Uploads are limited to known image/video types and stored by content hash.
- **Secrets:** bot tokens in `config/secrets.json` (mode 600); profiles hashed; passwords scrypt;
  `config/starnet.json` mode 600.
- **Shared surface:**
  - Writes are checked by `/api/surface/check`: cross-city, instruction, secrets and injection quarantine,
    with a red-team corpus.
  - The dashboard's read is read-only by construction.
- **StarNet:** stations bind to 127.0.0.1; `/v1` has a random 48-character key per station; ungranted actions
  are refused.
- **Network:** everything binds to localhost by default; remote access over Tailscale only.

## 19. Known limits and risks

- **Where the demo was tested:** on the MacBook, and in Chrome; other browsers are likely fine but weren't
  checked.
- **Social:** no platform connected; posting and replies are by hand. Demo videos are placeholders.
- **StarNet:**
  - World agents aren't crew on the station floor yet.
  - Stations open only on the PC.
  - Each needs a model provider.
  - StarNet runs anything granted in its station, with real cost: watch budgets there.
- **The Hermes link isn't built:** conversations use StarNet sessions built from ledger data, or the Mayor
  bot, not the agent's own Mnemosyne memory yet.
- **The shared surface:**
  - The tags depend on Hermes writing them (section 11.4).
  - The read-only view shows the newest 5,000 notes. Notes with the exact same timestamp as the last read
    could in rare cases be missed until the next new note.
- **The ledger can't see Telegram/Hermes messages,** so "the Mayor doesn't give orders to shadows" and daily
  ledger recording are enforced Hermes-side.
- **No automated backups** of `world.db`.
- **Deleting departments/districts** works only when empty; there's no move-all.
- **Professors' "teaching strikes" rules are free text** until the school system spec arrives.
- **The 3D views need a GPU;** very old laptops fall back to Details.
